## 0. Резюме для принятия решения

AutoDataAnalysis — **не сломанный и не демонстрационный проект**. Это работающий инструмент
на ~7 800 строк backend, ~11 100 строк frontend и ~2 600 строк тестов, у которого зелёные все
quality gates и нет ни одного TODO/stub/mock в продуктовом коде.

Поэтому вывод аудита не «переписать с нуля», а:

> **DataArena — это не новый проект, а извлечение data-слоя AutoDataAnalysis
> с заменой одного архитектурного решения (stateless multipart → серверный workspace)
> и одного слоя исполнения (eager Polars + regex-guard SQL → lazy Polars + DuckDB-sandbox).**

Готового к переносу кода — примерно **1 900 строк backend** (профилирование, чтение форматов,
ETL-движок, рекомендации, сравнение профилей, error-контракт, конфиг) и **весь frontend-каркас**
(транспорт, обработка ошибок, дизайн-система, ErrorBoundary).

Главное ограничение, которое делает прямое переиспользование невозможным без переработки,
одно и оно архитектурное: **у backend нет состояния**. Каждая операция — это повторная
загрузка файла целиком через multipart. Это блокирует workspace на несколько датасетов,
историю SQL, pipeline, undo/redo, lineage и recipes, то есть 8 из 10 ключевых требований DataArena.

## 2. Что работает — и работает честно

Это важная часть аудита: перечисленное ниже проверено, и его **нельзя выбрасывать ради новой архитектуры**.

### 2.1 Чтение форматов — `backend/datasets/io.py` (254 строки)

Поддержано 6 расширений: `.csv`, `.parquet`, `.json`, `.jsonl`, `.ndjson`, `.xlsx`.

Не декларативно, а с реальной работой над краевыми случаями:

- автоопределение разделителя CSV через `csv.Sniffer` с перебором `, ; \t |`;
- каскад кодировок: UTF-16 BOM → UTF-8-SIG → cp1251/cp1252/latin-1, причём **выбор между
  cp1251 и cp1252 делается по доле кириллицы в декодированном тексте** (порог 5% от букв,
  минимум 3 символа). Это редко встречающаяся и правильная деталь;
- `.json` пробует обычный массив, при неудаче переключается на NDJSON;
- Excel нормализует три возможных типа результата `pl.read_excel` (DataFrame / Series / dict листов);
- SHA-256 отпечаток файла считается потоково чанками по 1 МБ.

**Ограничение:** всё чтение — eager (`pl.read_*`). Нет ни одного `pl.scan_*`.

### 2.2 Профилирование — `backend/profiling/` (795 строк)

Считается на каждую колонку: dtype, семантический тип, пропуски (count/ratio), valid, unique
(count/ratio), константность, признак ID, дисбаланс, доминирующее значение, выбросы по 1.5·IQR,
5 примеров, `min/max/mean/median/std/q1/q3/skewness`, top-5 значений.

Две эвристики заслуживают отдельного упоминания, потому что сделаны аккуратнее, чем обычно:

- **детекция ID** не сводится к «в имени есть id». Порог уникальности 0.98 + пропусков ≤1% +
  разделение случаев: имя похоже на ID → да; числовая колонка → только если это строгий
  автоинкремент (целые, начало с 0 или 1, все diff == 1) — то есть отсортированная цена
  не будет объявлена идентификатором; нечисловая → да. И на каждое решение возвращается
  `id_reason` — человекочитаемая причина;
- **детекция дат в строковых колонках** идёт по данным (парсится ли ≥90% выборки из 200 значений),
  а не по подстроке в имени. Комментарий в коде прямо фиксирует, что прежняя эвристика
  превращала `runtime` и `update_flag` в даты.

**Quality Score** — 8 взвешенных штрафов (веса 10–60), линейная формула, и главное — она
возвращается не числом, а разложением: `key / label / ratio / weight / penalty / explanation`
на каждый компонент. Это честная конструкция: она не притворяется метрикой, она объясняет себя.

### 2.3 ETL — `backend/etl/` (865 строк)

Работает: `single` / `concat` (diagonal_relaxed) / `join` по одному ключу (inner/left/full),
поколоночные правила (include, cast, missing, outliers, rename, one-hot), вычисляемые колонки
через `pl.sql_expr` (**не** Python `eval` — важное решение), глобальная стратегия пропусков,
дедупликация, профили «до/после» и структурированное сравнение.

`_encode_one_hot_columns` отдельно решает нетривиальный случай коллизии имён dummy-колонок
через `max_horizontal` — это не boilerplate, это результат встречи с реальной ошибкой.

`recommendations.py` (340 строк) выдаёт детерминированные предложения с полями
`reason / expected_effect / confidence / severity / patch`. Проверено запуском на демо-данных:
5 рекомендаций, включая `merge_concat`, `exclude_id_and_constant: customer_id`,
`fill_missing_by_type: age, city, monthly_spend`, `clip_outliers: support_tickets, monthly_spend`.
Каждая — с точечным patch для применения одной кнопкой. **Это прямой прототип Smart Join
Suggestions из ТЗ DataArena.**

### 2.4 Контракт ошибок и безопасность загрузок

Единый формат `{"error":{"code","message","details"},"detail":"..."}` для доменных ошибок,
ошибок валидации FastAPI, HTTP-ошибок Starlette и непредвиденных исключений. Иерархия
`AppError` с осмысленными статусами (413/415/422/409/502). Внутренности стека наружу не уходят,
значения полей из ошибок валидации вырезаются, чтобы не утекли пользовательские данные.

Загрузки: `Path(filename).name` против path traversal, проверка расширения до записи,
запись чанками по 1 МБ с прерыванием на превышении лимита (200 МБ на файл, 500 МБ на запрос),
`TemporaryDirectory` с гарантированной уборкой, отказ на пустом файле.

### 2.5 ML-слой (уходит в ModelArena) — `backend/ml/` (2 984 строки)

Реален и не является предметом этого проекта, но фиксирую состав, потому что он определяет
границу разделения: обучение 4 моделей на задачу (включая всегда обучаемый baseline),
splits (random/stratified/temporal/group + auto-выбор), leakage-инспектор (487 строк),
error analysis, permutation importance, bootstrap-интервалы, verdict, inference с валидацией
схемы и проверкой новизны строк, файловое хранилище экспериментов с `joblib`-артефактами
и `Protocol`-интерфейсом под замену на БД/MLflow.

### 2.6 Frontend

React 19 + TypeScript 5.8 + Vite 7, **без UI-фреймворка** — 3 605 строк собственного CSS.
Единый транспортный слой `api/client.ts` с разделением `ApiError` / `NetworkError`,
единый `endpoints.ts`, `ErrorBoundary`, восстановление сессии из IndexedDB после F5.
6 разделов: Overview, Explore, Prepare, Model, Evaluate, Test Drive.

Зависимостей ровно три: `react`, `react-dom`, `lucide-react`. Это хорошая база.

## 3. Критичные находки для DataArena

### 🔴 A-1. Backend не имеет состояния — каждая операция перезагружает файл целиком

Это **главная находка аудита**.

Все содержательные endpoints принимают `UploadFile` в multipart:

```
POST /api/analyze              file=<весь файл>
POST /api/data/view            file=<весь файл>  config={offset,limit,sql,search}
POST /api/etl/preview          files=<все файлы> config=<recipe>
POST /api/etl/export           files=<все файлы> config=<recipe>
POST /api/etl/recommendations  files=<все файлы>
```

«Workspace» физически находится в браузере: `frontend/src/hooks/workspaceStorage.ts` хранит
`File`-объекты в IndexedDB и заново отправляет их на сервер при каждом переключении страницы,
поиске и SQL-запросе. `DatasetCache` (LRU, 4 таблицы / 512 МБ, ключ — SHA-256 содержимого)
существует ровно для того, чтобы смягчить это решение: он не даёт разбирать один и тот же файл
десятки раз, но **не отменяет передачу 64 МБ по сети на каждое нажатие «следующая страница»**.

Измерено: страница `offset=10000` на 1M строк — 0.34 с при полностью прогретом кеше.
Из них разбор файла — 0 мс; это стоимость передачи и повторного хеширования 64.6 МБ.

Что этим блокируется в требованиях DataArena:

- workspace с несколькими одновременно открытыми датасетами (п. 3) — только в браузере, сервер о них не знает;
- SQL history и Saved Queries, переживающие restart (п. 5) — некуда сохранять;
- transformation pipeline с undo/redo (п. 8) — нет объекта, к которому pipeline привязан;
- Dataset Builder (п. 9) — сборка из нескольких источников превращается в загрузку всех файлов на каждый шаг;
- lineage и recipes (п. 15, 16) — нечего версионировать;
- large data (п. 21) — потолок упирается в лимит 200 МБ на файл и в объём браузерной памяти.

**Вывод: это не рефакторинг, а замена архитектурного основания. Именно поэтому DataArena —
отдельный репозиторий, а не ветка.**

### 🔴 A-2. SQL-песочница построена на denylist регулярками — и это доказуемо слабее доступной альтернативы

`backend/dataview/sql_guard.py` защищает `pl.SQLContext` списком запрещённых функций
(`read_*`, `scan_*`, `from_*`, 12 явных имён) и ключевых слов (16 штук), плюс проверка
первого слова и запрет `;`.

Попытки обхода на живом сервере отбиты корректно (`read_csv`, `UNION ALL ... read_csv` и др.).
Ложных срабатываний на легитимных запросах в моих пробах не было (`AS unnested`, `WHERE city='set'`
проходят, потому что строки и идентификаторы обрабатываются до проверки).

Но это конструкция, которая **защищает включённую по умолчанию опасную возможность**.
Каждая новая табличная функция в Polars — потенциальная дыра, о которой узнают постфактум.

**Проверенная альтернатива.** Я поднял DuckDB 1.5.5 в изолированном venv и замерил:

| Конфигурация | `read_csv('C:/Windows/win.ini')` | `glob('C:/Users/<user>/*')` | `COPY ... TO 'C:/Users/<user>/leak.csv'` | `INSTALL httpfs` |
|---|---|---|---|---|
| `allowed_directories=[workspace]` + `lock_configuration=true` | ❌ **прочитал файл** | ❌ **выдал листинг домашней папки** | ❌ **записал 64 МБ наружу** | ❌ разрешено |
| `register(...)` → `enable_external_access=false` + `lock_configuration=true` | ✅ PermissionException | ✅ PermissionException | ✅ PermissionException | ✅ PermissionException |

Первая строка — **отдельная находка, которую стоит запомнить: `allowed_directories` сам по себе
не является песочницей.** Я на этом обжёгся в ходе проверки и создал два лишних файла по 64 МБ
в домашней папке (удалены сразу же).

Рабочая конфигурация — вторая: датасеты регистрируются как in-memory Arrow/Polars relations
**до** блокировки, затем движку выключается доступ к внешнему миру целиком и конфигурация
запирается. Это allowlist вместо denylist: запрещено всё, кроме зарегистрированных таблиц.

Производительность той же конфигурации (1M строк в памяти):

| Операция | DuckDB (register → lock) | Текущий стек (Polars eager + HTTP) |
|---|---|---|
| `count(*)` | 0.117 с (первый вызов), далее ~0 | — |
| `GROUP BY country` | **0.010 с** | 0.41 с (включая передачу 64 МБ) |
| страница `LIMIT 50 OFFSET 500000` | **0.021 с** | 0.34 с |
| `JOIN` 1M × 100k по ключу | **0.025 с** | такой возможности нет вообще |

Остаточный момент: DDL (`CREATE TABLE t AS SELECT 1`) внутри сессии остаётся разрешён.
Для эфемерного in-memory соединения это безвредно, но проверка «только читающие statements»
остаётся как второй рубеж.

### 🟡 A-3. Экспорт только в CSV

`POST /api/etl/export` возвращает единственный формат — CSV в UTF-8-SIG с фиксированным
именем `training_dataset.csv`. При этом читается 6 форматов. Асимметрия чтения и записи —
прямое нарушение требования п. 14 ТЗ.

Проверено, что ограничение снимается почти бесплатно: `polars 1.44.1` умеет писать
`csv / parquet / json / ndjson / ipc / excel / avro` без установки `pyarrow`.
Round-trip выполнен на таблице с int/float/str/bool/date/datetime и null в каждой колонке:

| Формат | schema сохранена | данные идентичны |
|---|---|---|
| Parquet | ✅ | ✅ |
| Arrow IPC / Feather | ✅ | ✅ |
| Avro | ✅ | ✅ |
| CSV (с `try_parse_dates`) | ✅ | ✅ |
| XLSX (`xlsxwriter` → `fastexcel`) | ✅ (Date остался Date) | ✅ |
| **JSON** | ❌ Date/Datetime → String | ❌ |
| **NDJSON** | ❌ Date/Datetime → String | ❌ |

Последние две строки — ровно тот случай, о котором ТЗ требует предупреждать пользователя
в Export Dialog. Теперь у предупреждения есть измеренное основание, а не общие слова.

### 🟡 A-4. Table Viewer не является таблицей уровня инструмента

`DataViewer.tsx` (443 строки) умеет: пагинацию (25/50/100, максимум сервера 200),
полнотекстовый поиск по всем колонкам, SQL, скрытие колонок, сохранение состояния в localStorage,
защиту от гонки запросов через счётчик.

Не умеет: **сортировку**, virtual scrolling, resize колонок, reorder колонок, индикаторы типа
и null в шапке, drill-down по клику на заголовок (dtype, null%, unique, min/max, распределение).
Из требований п. 4 ТЗ выполнено примерно 40%.

### 🟡 A-5. ETL — это конфигурация, а не pipeline

`EtlRecipe` — плоская структура с фиксированным порядком применения, зашитым в
`_execute_etl_on_frames`: merge → column rules → calculated → missing → dedup.

Пользователь не может: изменить порядок шагов, удалить один шаг, посмотреть промежуточный
результат после шага 3, отменить последнее действие. Undo/Redo отсутствует полностью.
Требование п. 8 ТЗ («каждое действие становится transformation step») не выполняется концептуально:
шага как объекта не существует.

При этом сами операции реализованы и протестированы — переносится содержимое, меняется форма.

### 🟡 A-6. Join — минимальный

Один ключ (не составной), три типа (нет `right`), суффикс жёстко `_file_N`, нет выбора колонок
с каждой стороны, нет предупреждения о размножении строк, нет анализа кардинальности,
нет предпросмотра join отдельно от полного ETL-preview. Требования п. 10–11 ТЗ выполнены
частично: `_recommend_merge` и `_select_join_key` угадывают ключ, но не считают ни overlap,
ни uniqueness, ни тип связи.

### 🟡 A-7. Пропущенные требования DataArena — реализованы на 0%

## 6. Итоговая оценка

| Аспект | Оценка | Комментарий |
|---|---|---|
| Качество кода | **высокое** | ruff + mypy + eslint + tsc чисто, единый стиль, комментарии объясняют «почему», а не «что» |
| Тесты | **хорошее** | 148 backend + 32 frontend, включая E2E smoke; нет тестов на большие данные и на производительность |
| Честность | **высокая** | нет фейковых метрик, нет кнопок-пустышек, ограничения названы вслух |
| Data-слой как основа DataArena | **пригоден на ~60%** | профилирование и IO переносятся почти целиком, ETL — по содержанию, API — нет |
| Архитектура для требований DataArena | **не подходит** | stateless multipart блокирует 8 из 10 ключевых требований |
| Безопасность | **приемлемая, но улучшаема** | denylist SQL работает, но allowlist доступен и проверен |
| Производительность | **лучше ожидаемого** | 1M строк профилируется за 0.98 с; узкое место — транспорт, а не вычисления |

**Рекомендация:** извлечь data-слой в DataArena с новым stateful ядром, перенести ML-слой
в ModelArena без изменения логики, `AutoDataAnalysis` оставить в архиве как read-only
референс и источник тест-кейсов.
