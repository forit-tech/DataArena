# Dataset Health — проект этапа

Состояние: **реализовано** (backend, API и интерфейс), 2026-09-09.
Проект согласован до реализации; ниже сохранён исходный текст, а в конце —
раздел о том, что при реализации изменилось и что измерено.

Цель этапа: объяснимая диагностика датасета с возможностью провалиться из находки
в конкретные строки.

**Чего здесь нет и не будет: сводной оценки качества.** Одно число вроде «87/100»
скрывает, какой именно дефект важен, и подталкивает улучшать число вместо данных.
Вместо него — независимые находки, каждая со своим масштабом, объяснением и способом
посмотреть затронутые строки.

---

## 1. Модель находки

```
Finding
  finding_id          устойчивый; см. §1.3
  code                устойчивый код проверки, из закрытого перечня
  severity            problem | warning | notice
  scope               dataset | column | column_pair
  columns             кортеж имён колонок (пусто для scope=dataset)
  affected_rows       int | None      — None, когда понятие «строки» неприменимо
  affected_ratio      float | None    — доля от общего числа строк
  exactness           exact | sampled — см. §3
  sampled_rows        int | None      — сколько строк просмотрено, если sampled
  evidence            ограниченная выборка: примеры значений, счётчики
  explanation         почему это важно и почему проверка сработала
  suggested_action    описание будущего шага преобразования | None; см. §6
  row_filter          описание предиката для провала в строки | None; см. §4
```

### 1.1 Уровни серьёзности

| Уровень | Что означает | Пример |
|---|---|---|
| `problem` | почти наверняка ошибка в данных | колонка целиком пуста |
| `warning` | вероятно ошибка, надо посмотреть | 40% пропусков; дубликаты строк |
| `notice` | сигнал, может быть совершенно нормальным | высокая кардинальность; выбросы |

**Жёсткое правило.** Следующие проверки **никогда** не поднимаются выше `notice`,
даже при любых значениях: высокая кардинальность, выбросы, похожесть на идентификатор,
редкая категория. Это свойства данных, а не дефекты. Правило закрепляется тестом,
перебирающим все коды: у перечисленных потолок жёстко ограничен.

### 1.2 Перечень проверок

Все коды — из закрытого перечня. Проверка, которая ничего не может найти в текущей
реализации, не заводится вовсе.

| Код | Что находит | Потолок | Точность | Провал в строки |
|---|---|---|---|---|
| `missing_values` | пропуски в колонке | warning | exact | да |
| `all_null_column` | колонка пуста целиком | problem | exact | вся колонка |
| `duplicate_rows` | полностью совпадающие строки | warning | exact | да |
| `duplicate_keys` | повторы в колонке, похожей на ключ | warning | exact | да |
| `constant_column` | ровно одно значение | notice | exact | нет |
| `near_constant_column` | одно значение чаще 99% | notice | exact | да, «всё кроме» |
| `high_cardinality` | много различных значений | **notice** | exact | нет |
| `potential_identifier` | значения уникальны на всех строках | **notice** | exact | нет |
| `mixed_semantic_types` | в одной текстовой колонке числа, даты и текст | warning | sampled → exact | да |
| `invalid_numeric` | нечисловые значения там, где остальное числа | warning | exact | да |
| `nan_or_infinity` | NaN и бесконечности в дробной колонке | warning | exact | да |
| `datetime_parse_anomaly` | значения, не разбираемые как дата, в колонке дат | warning | exact | да |
| `outlier_values` | значения далеко за межквартильным размахом | **notice** | exact | да |
| `whitespace_anomaly` | ведущие и хвостовые пробелы | warning | exact | да |
| `empty_string_vs_null` | в колонке есть и пустые строки, и пропуски | notice | exact | да |
| `case_variant_categories` | значения, различающиеся только регистром или пробелами | warning | exact | да |

**`schema_drift` намеренно не заводится сейчас.** Датасет сегодня — один артефакт,
частей у источника нет, и проверка не смогла бы сработать ни разу. Она появится вместе
с многочастными источниками. Заводить код, который никогда не срабатывает, — то же
самое, что кнопка без действия.

### 1.3 Идентификатор находки

```
finding_id = "fnd_" + sha256(dataset_id | artifact_fingerprint | code | columns)[:16]
```

Три следствия, ради которых он именно такой:

* **воспроизводимость** — повторное открытие Health даёт те же идентификаторы,
  и ссылка на находку переживает перезагрузку страницы;
* **обнаружение устаревания** — в идентификатор входит отпечаток артефакта; после
  пересборки артефакта старая ссылка перестаёт разрешаться, и это видно как отдельный
  ответ, а не как показ других строк;
* **отсутствие состояния** — идентификатор не надо хранить, чтобы выдать; он выводится.

## 2. Устойчивая идентичность строки

### Решение

**Порядковый номер строки в артефакте** (`row_ordinal`, с нуля), вместе с отпечатком
артефакта. Не номер на странице, не номер после сортировки.

### Почему это работает — измерено, а не предположено

На 300 000 строк, parquet и csv:

* порядок чтения **детерминирован между прогонами** — три прогона дали одни и те же
  номера для одних и тех же строк;
* номер **переживает сортировку и фильтр**: страница берётся после `sort`, затем по её
  номерам находятся ровно те же строки;
* номер **не зависит от плана**: наличие сортировки в плане его не меняет;
* он **ничего не стоит**: время и пик памяти при добавлении номера не изменились,
  фильтр по номеру отрабатывает за 0,02 с с нулевым приростом памяти.

### Что с этим не так и как это ограничено

1. **Это свойство текущего читателя, а не закон.** Многочастный источник, параллельное
   или потоковое чтение могут порядок изменить. Поэтому: идентичность привязана
   к отпечатку артефакта, а детерминированность закрепляется отдельным тестом, который
   покраснеет при смене читателя. Утверждение «номер устойчив» перестанет быть верным
   молча — оно перестанет быть верным громко.
2. **Артефакт, а не источник.** Для нормализованных форматов номер относится к тому
   parquet, который читается на самом деле. Провал в строки читает его же, поэтому
   расхождения быть не может. Совпадение порядка source → derived требует отдельной
   проверки и не предполагается.
3. **Столкновение имён.** Внутренняя колонка номера получает имя, которого нет в схеме
   датасета (подбор свободного имени), и **не попадает в состав строки** в ответе API:
   она отдаётся отдельным полем. Иначе датасет с колонкой `__ordinal__` сломал бы
   и таблицу, и провал в строки.

## 3. Точное против выборочного

**Правило одно: любое показанное число либо точное, либо помечено выборочным. Третьего
состояния нет.**

* Отбор кандидатов может идти по выборке — это дёшево и не требует точности.
* Находка, **называющая количество**, обязана иметь точное количество, либо нести
  `exactness = sampled` и `sampled_rows`, и интерфейс обязан показать это словами,
  а не значком.
* Проверка не имеет права понизить точность молча: `exactness` — обязательное поле
  модели, а не необязательное.

Сегодня выборка нужна ровно одной проверке — `mixed_semantic_types`: определять смесь
типов по каждому значению большого датасета дорого. Схема такая: кандидат находится
по выборке, затем количество считается точно предикатом. Если точный подсчёт выходит
за отведённый бюджет, находка публикуется как `sampled` с честным числом просмотренных
строк.

## 4. Провал в строки: предикат, а не список номеров

### Решение

Находка несёт **описание предиката** из закрытого перечня:

```
RowFilter
  kind    is_null | is_not_null | equals | not_equals | in_values |
          is_nan_or_inf | matches_normalised | out_of_range | duplicated_by | ordinals
  column  имя колонки (или колонок для duplicated_by)
  ...     параметры, зависящие от kind; все ограничены по размеру
```

Провал в строки — это **существующий постраничный запрос таблицы** с дополнительным
параметром `finding_id`. Сервер разрешает его в предикат и применяет вместе с обычными
сортировкой, фильтрами и поиском. Отсюда бесплатно берётся всё, что уже работает:
виртуализация, страницы, сортировка внутри найденных строк.

### Ключевой инвариант

**Один и тот же объект предиката используется и для подсчёта в находке, и для показа
строк.** Не «эквивалентная логика» — тот же объект. Иначе однажды находка скажет «127
строк», а таблица покажет 119, и доверия к разделу не останется.

Инвариант проверяется тестом по **каждой** находке на нескольких датасетах:
`count(row_filter) == affected_rows`.

### Почему не список номеров

Находка на миллион затронутых строк дала бы список на миллион чисел — в ответе, в базе,
в браузере. `kind = ordinals` допускается только для маленьких множеств (предел
зафиксирован константой) и только там, где предикат выразить нельзя.

## 5. Ленивое и ограниченное выполнение

* **Один проход на батарею колоночных показателей.** `null_count`, `n_unique`, границы,
  счётчики по типам собираются одним `select` над `LazyFrame`. Измерено: девять
  показателей на 300 000 строк — 0,02 с, прирост памяти ноль. Отдельный проход
  на колонку означал бы N проходов вместо одного.
* **Отдельные проходы только там, где иначе нельзя**: полные дубликаты строк,
  межквартильный размах.
* **Широкие датасеты дробятся по группам колонок**: тысяча колонок × несколько
  показателей — это тысячи выражений в одном плане, и план надо ограничивать.
* **Ничего не материализуется целиком.** Наружу выходят только агрегаты и ограниченная
  выборка примеров.
* **Отчёт кэшируется** по ключу `(dataset_id, artifact_fingerprint, checks_version)`.
  Смена любого из трёх — пересчёт. Кэш хранит находки без строк.

Измерено (`scripts/measure_health.py`):

| Датасет | Время | Пик памяти | Находок |
|---|---|---|---|
| 100 000 строк × 6 колонок | 0,09 с | 0,0 МБ | 9 |
| 1 000 000 строк × 6 колонок | 0,38 с | 0,0 МБ | 9 |
| 20 000 строк × 500 колонок | 2,08 с | 0,5 МБ | 9 |
| 5 000 строк × 1 000 колонок | 4,10 с | 0,6 МБ | 9 |

Главное здесь не время, а вторая колонка: **пик памяти не зависит от числа строк**.
Рост в тысячу раз по строкам не изменил его вовсе — наружу выходят только агрегаты.

**Про долгий расчёт.** Если расчёт не укладывается в разумное время синхронно, честных
выходов два: сделать проверку выборочной и пометить её, либо завести настоящий слой
фоновых задач. Показывать полосу загрузки, за которой ничего нет, — не выход.
Решение принимается по результатам измерения, а не заранее.

## 6. Связь находки с будущим преобразованием

Health **ничего не исправляет и ничего не пишет**. Датасет остаётся неизменным.

`suggested_action` — это **описание** будущего шага, а не действие:

```
SuggestedAction
  kind       drop_column | fill_missing | drop_duplicates | trim_whitespace |
             normalise_case | cast_type | drop_rows
  columns    к чему применяется
  parameters параметры, зависящие от kind
```

Когда появится этап преобразований, кнопка «исправить» будет **создавать шаг
преобразования** из этого описания — с исходным снимком, самим шагом и производным
снимком в происхождении. Она не будет менять исходный артефакт: это уже зафиксировано
контрактом Dataset Package и не пересматривается.

До этого этапа `suggested_action` показывается как текст рекомендации. Кнопки, которая
ничего не делает, в интерфейсе не будет.

## 7. Модель угроз и отказов

Раздел о том, что может пойти не так. Порядок — по тяжести последствий.

| № | Отказ | Последствие | Чем закрывается |
|---|---|---|---|
| F-1 | Выборочное число показано как точное | Неверное решение по данным: «пропусков 2%» вместо 40% | `exactness` — обязательное поле; тест на каждую проверку; мутация «пометка точности снята» |
| F-2 | Провал в строки показывает не то, что посчитала находка | Разрушено доверие ко всему разделу | Один объект предиката на подсчёт и на показ; тест `count(filter) == affected_rows` по каждой находке |
| F-3 | Идентичность строки взята из страницы | После сортировки «строка 143» — другой объект | Порядковый номер артефакта; тест: отсортировать, провалиться, сверить те же строки |
| F-4 | Находка устарела после пересборки артефакта | Показаны строки другого артефакта | Отпечаток в идентификаторе находки; устаревшая ссылка → отдельный ответ, а не другие строки |
| F-5 | Колонка называется как внутренняя колонка номера | Сломаны и таблица, и провал | Подбор свободного имени; номер отдаётся отдельным полем; тест с колонкой `__ordinal__` |
| F-6 | Расход памяти растёт с числом строк | Health невозможно открыть на большом датасете | Только агрегаты; дробление по группам колонок; измерение на 1M и 1000 колонок |
| F-7 | Датасет читается таблицей, но не полностью читается проверками | Ответ 500 вместо объяснения | Доменная ошибка с названием датасета — как в R-47 |
| F-8 | Расчёт идёт минутами | Интерфейс выглядит зависшим | Измерить; либо выборочность с пометкой, либо настоящий слой задач. Фальшивого прогресса не будет |
| F-9 | Датасет удалён во время расчёта | Необработанное исключение | То же окно проверки и использования, что уже закрыто в SQL: доменная ошибка |
| F-10 | В примерах значений NaN, бесконечности, управляющие символы, огромные строки | Сломанный JSON или сломанная вёрстка | `json_safe_value` (уже есть) + обрезка длины |
| F-11 | Находка выкладывает слишком много значений | Раздутый ответ и база | Жёсткий предел на число примеров |
| F-12 | Сигнал показан как дефект | Пользователь «чинит» нормальные данные: удаляет идентификатор, режет выбросы | Потолок `notice` для четырёх проверок, закреплённый тестом |
| F-13 | Значения из данных попадают в разметку интерфейса | Порча вёрстки или хуже | React экранирует по умолчанию; никакого `dangerouslySetInnerHTML`; проверка на значении вида `<script>` |
| F-14 | Кэш отдаёт отчёт другого датасета | Полностью неверная диагностика | Ключ включает рабочее пространство, датасет и отпечаток |
| F-15 | Пустой датасет: деление на ноль в доле | Падение расчёта | Отдельная ветка для нуля строк; доля `None`, а не ноль |
| F-16 | Датасет из одной строки: «константная колонка» на каждой колонке | Отчёт из мусора | Проверки с минимальным числом строк; ниже порога не срабатывают и объясняют почему |

## 8. Что войдёт в приёмку этапа

Помимо обычных ворот (`pytest`, `ruff`, `mypy`, `eslint`, `tsc`, `vitest`, сборка,
`pip-audit`, `npm audit`):

* **враждебные случаи**: 0 строк, 1 строка, 1 000 000 строк, 1 000 колонок, колонка
  целиком из пропусков, колонка из одинаковых значений, `bool`, `decimal`, часовые
  пояса, Unicode, огромные строки, повторяющиеся имена колонок, NaN и бесконечности,
  испорченные даты, пустая строка против пропуска, значения, различающиеся только
  регистром и пробелами, находка на миллион затронутых строк;
* **измерения**: 100k, 1M, широкий датасет; ограниченность памяти;
* **мутации**: обнаружение дубликатов, обнаружение пропусков, соответствие находки
  и строк, устойчивость идентичности строки, подтверждение выборочного точным,
  серверная фильтрация затронутых строк — каждая обязана красить тест;
* **живая сквозная проверка**: датасет → Health → находка → открыть строки →
  сортировка и фильтр внутри них → назад к датасету → перезапуск backend →
  датасет и находки согласованы, исходный артефакт не изменился;
* **отдельный разбор** по тому же порядку, что и для Этапа 3, с записями в
  `SECURITY_AND_ROBUSTNESS_REVIEW.md`.

Статус PASS по итогам разбора предлагается, но не объявляется исполнителем.

## 9. Открытые вопросы к согласованию

1. **Пороги.** «Почти константная» — 99%? «Высокая кардинальность» — от какой доли
   уникальных? Предлагаю зафиксировать числами в коде с объяснением, а не делать
   настройками: настройка, которую никто не трогает, — это спрятанное решение.
2. **Провал в строки для `constant_column` и `potential_identifier`.** Затронуты все
   строки. Показывать всю таблицу или не давать провал вовсе? Предлагаю не давать:
   «показать все строки» — это просто открыть датасет.
3. **Порядок находок в отчёте.** По серьёзности, затем по доле затронутых строк,
   затем по имени колонки — чтобы порядок был устойчивым между открытиями.
4. **Пересчёт.** Автоматически при открытии, если отпечаток не совпал, или по явной
   кнопке? Предлагаю автоматически: устаревший отчёт хуже, чем ожидание.

## 10. Что изменилось при реализации

Проект не менялся по существу, но несколько вещей выяснились только на данных.

### Устойчивость строки оказалась нужна не для провала

Провал в строки описан предикатом, поэтому **идентичность отдельной строки для него
не требуется**: находка говорит «строки, где значение пусто», а не «строки 143 и 287».
Номер строки всё равно реализован и показан в таблице, но у него другая задача — отвечать
на вопрос «какая это строка файла», когда человек смотрит на отфильтрованное подмножество.
На снимке провала это видно сразу: номера идут 1, 2, 5, 6, 9, 10, 13… — не подряд, потому
что это номера файла, а не позиции на странице.

### Служебная колонка чуть не сломала поиск дубликатов

При подсчёте полных дубликатов через «все колонки плана» в набор попадала служебная
колонка с номером строки — и каждая строка становилась уникальной. Измерено: результат
был ноль вместо сорока. Колонки перечисляются явно, и на это есть отдельная проверка
и отдельная мутация.

### NaN попадал сразу в две находки

Без исключения неконечных значений выбросами объявлялись ровно те же строки, что уже
названы в находке про NaN. Человек видел одну проблему под двумя заголовками. Предикат
диапазона теперь исключает неконечные значения для дробных колонок.

### Выборочность оказалась настоящей, а не декоративной

Порог приближённой кардинальности — 20 миллионов клеток. Проверено на датасете
1 000 000 × 25: находка `potential_identifier` возвращается с пометкой «оценка
по выборке» и числом просмотренных строк. Поле точности не украшение — оно меняется.

### Согласование числительных

«1 значений записаны по-разному», «9 Предупреждение», «5 Сигнал» — тексты находок читает
человек и по ним принимает решение, и сломанное согласование выглядит так же, как
сломанный расчёт. Заведены `backend/domain/health/wording.py` и `plural` во фронтенде,
обе стороны покрыты тестами на 1, 2, 4, 5, 11, 21, 101, 111, 1002.

### `schema_drift` так и не заведён

Как и записано в §1.2: датасет — один артефакт, проверка не сработала бы ни разу.
Кода, который никогда не срабатывает, в перечне нет.

### Что осталось несделанным

Отдельный враждебный разбор этапа, как для Этапа 3. Он предусмотрен §8 и **не проводился**:
статус PASS без него не предлагается.
