# Технические риски DataArena

Оценка: **вероятность × влияние**. Риски отсортированы по совокупной опасности.
Там, где риск уже проверен экспериментом, указан результат — это меняет оценку.

---

## 🔴 R-1. Память при материализации больших датасетов

**Вероятность: высокая. Влияние: высокое.**

Часть операций нельзя выполнить лениво: полный профиль требует прохода по всем значениям,
корреляционная матрица — материализованных числовых колонок, `unique()` для дедупликации —
хеш-таблицы по всему датасету. На 1M × 7 это безопасно (Parquet 12.5 МБ, в памяти ~50 МБ),
на 50M × 200 — нет.

Кеш материализованных версий делает риск хуже: несколько датасетов одновременно × несколько
версий pipeline = кратный расход.

**Что делаем:**
- бюджет памяти в конфиге, учёт `estimated_size()` перед материализацией — приём уже
  применён в `DatasetCache` AutoDataAnalysis;
- отказ с понятным сообщением и предложением выборки вместо OOM;
- профилирование по выборке для датасетов сверх порога, с обязательным флагом
  `sampled: true` в profile (см. контракт package);
- LRU-вытеснение версий, приоритет — активному датасету;
- performance-тесты с порогом по пиковой памяти, а не только по времени.

**Остаточный риск:** пороги придётся подбирать эмпирически; первый выбор наверняка окажется неточным.

## 🔴 R-2. Комбинаторная сложность pipeline + undo/redo + reorder

**Вероятность: высокая. Влияние: высокое.**

Reorder шагов безопасен только при отсутствии зависимости по колонкам. Но зависимости
не всегда очевидны: `derive` с SQL-выражением читает колонки, которые надо распарсить;
`filter` по колонке, которую предыдущий шаг переименовал; `deduplicate` по колонке,
созданной шагом выше. Ошибка в анализе зависимостей = молчаливая порча данных —
худший класс ошибок для инструмента работы с данными.

**Что делаем:**
- каждый шаг обязан явно объявлять `reads: set[str]` и `writes: set[str]`;
- для `derive` колонки извлекаются из разобранного выражения, а не угадываются;
- **правило по умолчанию — запрет:** если зависимость определить не удалось, reorder
  запрещён, и UI объясняет причину. Ложный отказ безопаснее ложного разрешения;
- property-based тесты: случайные pipeline, проверка что replay после разрешённой
  перестановки даёт идентичный результат;
- `validate(schema)` перед применением каждого шага — ошибка до выполнения, а не в середине.

## 🟠 R-3. Возврат к denylist в SQL под давлением удобства

**Вероятность: средняя. Влияние: критическое.**

Конфигурация «register → lock» проверена и работает (AUDIT A-2), но она неудобна:
чтобы добавить датасет в SQL-сессию, его нужно материализовать заранее. Возникнет
искушение «просто разрешить `read_parquet` для файлов workspace» — и защита схлопнется
в тот же denylist.

Проверено, что промежуточного варианта нет: `allowed_directories` **не является песочницей** —
при включённом `enable_external_access` DuckDB 1.5.5 прочитал `C:/Windows/win.ini`, выдал
листинг домашней папки и записал файл наружу.

**Что делаем:**
- security-тест с набором попыток обхода, который **обязан падать** при ослаблении конфигурации;
- порядок вызовов зафиксирован в одном месте (`DuckDBSession`), а не рассыпан по коду;
- ADR с записью, почему `allowed_directories` отвергнут, — чтобы решение не пересматривали
  по забывчивости;
- на больших датасетах вместо ослабления песочницы — регистрация Arrow-представления
  без копирования.

**Остаточный риск:** новые версии DuckDB могут изменить поведение настроек. Security-тест
поймает это при обновлении.

## 🟠 R-4. Своя виртуализация таблицы окажется хуже готовой

**Вероятность: средняя. Влияние: среднее.**

Virtual scrolling + resize + reorder + sticky-заголовки + горизонтальный скролл +
переменная ширина колонок — сочетание, где легко получить дёрганый скролл и рассинхрон
заголовка с телом таблицы. Это самая заметная часть интерфейса: если тормозит она,
не важно, как быстр backend.

**Что делаем:**
- сначала фиксированная высота строки — это снимает большую часть сложности;
- измеримый критерий: плавный скролл по 1M строк, отклик на сортировку < 300 мс;
- если свой вариант не проходит критерий — переход на `@tanstack/react-virtual`
  без сожалений, с записью решения в README;
- граница принятия решения — конец Этапа 2, а не «когда-нибудь потом».

## 🟠 R-5. Разъезд контракта Dataset Package между сервисами

**Вероятность: средняя. Влияние: высокое.**

Два репозитория, один контракт. Классический сценарий: DataArena добавляет поле,
ModelArena не знает, интеграция ломается молча.

**Что делаем:**
- **golden package** в обоих репозиториях как единственный источник истины;
- JSON Schema, валидация с обеих сторон;
- тест отказа: неизвестная мажорная версия отвергается с внятным сообщением,
  а не читается «как получится»;
- правила semver зафиксированы в контракте;
- незнакомые поля игнорируются потребителем — это делает minor-изменения безопасными.

## 🟡 R-6. Определение формата по расширению

**Вероятность: средняя. Влияние: среднее.**

Расширение — не доказательство содержимого. `.csv`, оказавшийся Excel-файлом,
`.json` с NDJSON внутри, Parquet без расширения. В AutoDataAnalysis это частично решено
(JSON пробует два варианта, CSV перебирает кодировки и разделители).

**Что делаем:**
- проверка magic bytes для бинарных форматов (Parquet `PAR1`, XLSX — ZIP-сигнатура,
  Arrow IPC `ARROW1`);
- перенос каскадных стратегий для CSV и JSON;
- при неудаче — понятное сообщение с тем, что было прочитано, без внутренностей стека;
- расширение остаётся быстрым первым фильтром, но не последним словом.

## 🟡 R-7. Размер и связность frontend

**Вероятность: средняя. Влияние: среднее.**

В AutoDataAnalysis `ModelsWorkspace.tsx` вырос до 655 строк, `EtlWorkspace.tsx` — до 607,
CSS — до 3 605 строк в двух файлах. Builder и таблица в DataArena сложнее всего, что там было.

**Что делаем:**
- feature-модули с собственным CSS, никакого общего `styles.css` на всё приложение;
- граница внимания — 300 строк на компонент; превышение требует обоснования, а не автоматического дробления;
- логика в hooks, компоненты — рендер и обработчики;
- контроль размера бандла в CI: превышение порога роняет сборку.

## 🟡 R-8. Соблазн затащить ML-функции обратно в DataArena

**Вероятность: средняя. Влияние: среднее.**

Корреляции, кардинальность, дисбаланс, кандидаты в target — всё это про ML. Отсюда полшага
до «а давай посчитаем feature importance» и «а давай baseline обучим». Граница размывается
незаметно, и получаются два сервиса, делающих одно и то же.

**Что делаем:**
- правило в одну строку: **DataArena не обучает моделей и не считает ML-метрик**;
- всё, что требует target для вычисления, — признак нарушения границы;
- `hints` в package — подсказки с причиной, а не решения;
- при сомнении функция уходит в ModelArena: обратный перенос дешевле распутывания.

## 🟡 R-9. Точность оценки числа строк после join

**Вероятность: средняя. Влияние: среднее.**

Предупреждение о row explosion полезно ровно настолько, насколько точна оценка.
Заниженная оценка = пользователь запускает join и получает 40M строк вместо ожидаемых 100k.
Завышенная = пугает без причины и перестаёт восприниматься всерьёз.

**Что делаем:**
- честная оценка по распределению кратностей ключа, а не по формуле `n × m`;
- показывать не одно число, а границы и тип связи;
- на больших датасетах — оценка по выборке с явным указанием, что это оценка;
- после выполнения сравнивать факт с оценкой и логировать расхождение — так качество
  оценки видно, а не предполагается.

## 🟢 R-10. Регрессия при переносе кода из AutoDataAnalysis

**Вероятность: низкая. Влияние: среднее.**

Перенос ~1 900 строк backend всегда несёт риск потерять краевой случай — например,
выбор cp1251/cp1252 по доле кириллицы или разрешение коллизий dummy-имён.

**Что делаем:**
- переносить **вместе с тестами**: 148 backend-тестов AutoDataAnalysis описывают поведение,
  которое надо сохранить;
- сначала тест, потом код, для каждого переносимого модуля;
- AutoDataAnalysis остаётся доступным для сверки поведения.

---

## 🟢 R-11. Обновления Polars и DuckDB

**Вероятность: низкая. Влияние: низкое.**

Уже видно приближение изменений: `FutureWarning` про `from_arrow` при `read_excel`
сработает на Polars 2.0. В AutoDataAnalysis верхняя граница `pandas<4.0` оказалась
настолько широкой, что установилась мажорная версия, которой при написании границ не существовало.

**Что делаем:**
- точные верхние границы: `polars>=1.44,<2.0`, `duckdb>=1.5,<2.0`;
- lock-файл;
- обновление major — отдельная задача с прогоном security- и round-trip-тестов,
  а не побочный эффект `pip install -U`.
