# CCR-001 — история колонок в `lineage.json`

| | |
|---|---|
| Статус | **ACCEPTED** 2026-09-25 |
| Автор | DataArena (владелец контракта) |
| Принятая версия | `dataarena.package/1.1.0` — MINOR |
| Затрагивает | `lineage.json`, `schema/lineage.schema.json`, `reference/validate_package.py`, `golden/lineage/` |
| Producer | DataArena: пишет `provenance` и `columns` с 1.1.0 |
| Consumer | ModelArena: читает, проверяет, хранит, показывает сводку |

Принято после того, как потребитель научился читать поля и прошёл тесты контракта —
а не наоборот: пакет, который производитель уже пишет, а потребитель, может быть, понимает,
не выпускался ни на одном шаге.

## Reason — зачем

Раздел «Происхождение» DataArena отвечает на вопрос, который ModelArena задаёт о признаках:
**откуда взялась колонка и что с ней делали**. До 1.1.0 ответ был в интерфейсе DataArena
и не доходил до потребителя пакета.

```text
customers.csv.email
  ↓ trim_whitespace          (датасет customers, шаг 1)
  ↓ fill_missing "?"         (датасет customers, шаг 2)
  ↓ LEFT JOIN                (customers ⋈ orders → customer_orders)
  ↓ change_case lower        (датасет customer_orders, шаг 2)
customer_orders.email
```

## Current contract — что было в 1.0.0

`sources[]`, `graph[]`, `row_count_trace[]`: граф описывает датасет целиком, но не говорит,
какой шаг изменил какую колонку, как она называлась раньше, с какой стороны соединения пришла,
и не умеет сказать «происхождение неизвестно» или «история неполна».

## Problem — чего не хватало

1. Шаг, **читающий** колонку, неотличим от шага, **меняющего** её.
2. Переименования разрывают связь с источником.
3. Сторону соединения нельзя вывести по именам (`total_2` слева против `total` справа с суффиксом `_2`).
4. «Неизвестно» и «неполно» невыразимы — их отсутствие читалось бы как «история чиста».

## Решение — два необязательных поля

Нормативное описание — [`dataset-package-v1.md`](dataset-package-v1.md), раздел
«С 1.1.0: `provenance` и `columns`»; схема — [`schema/lineage.schema.json`](schema/lineage.schema.json).

**`provenance`** — `{status, origin, unknown_reason, history, warnings}`. Три состояния,
которые потребитель обязан различать:

| Состояние | `status` | `history` |
|---|---|---|
| известно и полно | `known` | `complete` |
| известно, но неполно (история родителя усечена, снимков нет, история колонок не уместилась) | `known` | `incomplete` + коды в `warnings` |
| неизвестно | `unknown` | `incomplete` |

Отсутствие `provenance` — «producer не сообщил» (пакеты 1.0.0), а не одно из трёх.

**`columns[]`** — по записи на колонку данных, в порядке данных:
`{name, origin, history, origins[0..N], events[], read_by[]}`.

Отличия от первоначального предложения (оно ссылалось на узлы графа обязательно):

- **Событие описывает себя само** (`dataset_id`, `dataset_name`, `position`, `operation`,
  `inputs`, `output`), а ссылка `node` на узел графа — необязательна. Причина — многоуровневые
  сборки: шаги прародителя входят в историю колонки внука, но узлов для них в графе пакета нет.
  Обязательная ссылка вынудила бы либо выдумывать узлы, либо терять события.
- **Источник колонки тоже описывает себя** (`dataset_id`, `column`, `source_file`,
  `source_sha256`); ссылка `source` на `sources[].id` — необязательна по той же причине.
- **`read_by`** — узлы графа (`n3`), а не номера шагов: единообразно со ссылками событий.
- **`origins` — список 0..N**: вычисляемая колонка «цена × количество» уже выражается,
  и следующее расширение не потребует переделки.

## Producer requirements (DataArena)

1. `columns` и `provenance` строятся **из ответа единого resolver'а** происхождения; своей
   логики вывода у сборщика пакета нет.
2. `columns` — ровно колонки данных, в их порядке; события — в хронологическом порядке
   resolver'а, без пересортировки.
3. `origin = unknown` ⇔ `origins` пуст. Ссылки `source` / `node` пишутся, только если такой
   источник или узел есть в пакете.
4. Описание шага длиннее 10 000 символов обрезается (это текст для человека). Если история
   не помещается в пределы схемы или в 16 MiB части, `columns` не пишется, в `warnings`
   добавляется `column_history_omitted`, `history` = `incomplete`.
5. Пакет с колонкой, чьё имя длиннее 300 символов (предел `schema.json`), не собирается:
   явный отказ `package_failed` вместо пакета, который отверг бы потребитель.
6. `format_version` = `1.1.0` в манифесте и во всех частях.

## Consumer requirements (ModelArena)

1. Пакет без `provenance` / `columns` читается как раньше; история — «не сообщено».
2. `columns` проверяется по схеме и по смыслу: имена = колонки данных в их порядке,
   `unknown` ⇔ пустые `origins`, ссылки существуют. Нарушение — `package_part_invalid`
   (часть, противоречащая пакету, не читается — как часть, не прошедшая схему).
3. Разбор любой JSON-части пакета — строгий: не-UTF-8, BOM, `NaN`/`Infinity`, повреждённый JSON →
   `package_part_invalid`; вложенность глубже 32 → `package_limit_exceeded`. Не пятисотка.
4. Незнакомое значение `status` читается как `unknown`, `history` — как `incomplete`;
   незнакомые поля, `operation` и `kind` игнорируются.
5. События не сортируются и не восстанавливаются: порядок нормативен.
6. История — метаданные для просмотра. **Не влияет** на обучение, разбиение, метрики,
   лидерборд, выбор модели и проверку утечек без отдельно определённой семантики.

## Limits

| Поле | Предел | Откуда |
|---|---|---|
| `columns[]` | 10 000 | как `sources[]` / `graph[]` в 1.0 |
| `origins[]` колонки | 1 000 | |
| `events[]` колонки | 10 000 | конвейер DataArena — до 200 шагов на уровень |
| `inputs[]` события | 100 | как `graph[].inputs` в 1.0 |
| строка (имя, описание) | 10 000 символов | как `MAX_TEXT` доменной модели DataArena |
| вся часть `lineage.json` | 16 MiB | §H, без изменений |
| глубина JSON | 32 | §H, без изменений; теперь проверяется эталоном и потребителем |

## Fingerprint semantics

`data.content_fingerprint` описывает **только значения данных** (§D) и от истории
не зависит: один датасет, собранный разными путями, имеет один отпечаток и один
`package_id`. История защищена `parts[].sha256` части `lineage.json`, как любая часть.
Закреплено тестом `test_data_identity_does_not_depend_on_history`.

Следовательно, ни отпечаток, ни `package_id` **не идентифицируют историю**: пакеты с одними
данными и разной историей имеют одинаковые оба значения. Потребитель, которому важна
история, обязан различать импорты сам, а не по этим полям. ModelArena так и делает:
идентичность снимка — данные **и** отпечаток `lineage.json` (без `created_at`); те же данные
с другой историей — другой снимок со своей историей, а файл данных хранится один раз.
Первоначальное решение «второй пакет возвращает первый снимок с его историей» отменено:
пакет B получал происхождение пакета A.

## Backward compatibility — проверено запуском

| Producer → Consumer | Результат |
|---|---|
| 1.0 (эталон `customers_golden`) → consumer 1.1 | принят, история «не сообщена» |
| 1.1 (фикстуры и реальный пакет DataArena) → эталонный валидатор 1.0 из `HEAD` | принят + warning «более новая minor» |
| 1.1 (фикстуры) → код ModelArena до изменения | принят + тот же warning; `columns` игнорируется |
| 1.1 → consumer 1.1 | принят без предупреждений; повреждённые варианты — отказ с кодом |

## Versioning decision

**MINOR, 1.0.0 → 1.1.0.** Добавлены два необязательных поля; ни одно существующее поле
не стало обязательным и не сменило смысла (§E). Алгоритм отпечатка не менялся. Эталонный
пакет 1.0.0 не пересобирался и остаётся валидным: он и есть «старый пакет» набора.

Отклонённая альтернатива — отдельная часть `columns.json`: тоже MINOR, но разрывает
ссылки событий на узлы `graph` между файлами.
