**Версия спецификации:** 1.0.0
**Статус:** **FROZEN** 2026-09-06. Все шесть условий §J выполнены и проверены запуском.

> версиях Polars. Подробности и доказательства — в §J.

## 0. Нормативные принципы

Семь правил, которым подчиняется всё остальное. Нарушение любого из них — breaking change.

1. **Никакого импорта кода между сервисами.** Пакет самодостаточен и читается любым
   инструментом, умеющим JSON и Parquet. ModelArena не импортирует Python-модули DataArena,
   DataArena не импортирует модули ModelArena.
2. **Канонический табличный артефакт — Parquet.** Round-trip проверен: типы и null сохраняются
   точно; CSV и JSON теряют Date/Datetime (см. [AUDIT.md](https://github.com/forit-tech/DataArena/blob/main/AUDIT.md), A-3).
3. **`profile` и `hints` — advisory only.** Это подсказки для показа человеку. Любое число,
   на котором потребитель строит решение, он пересчитывает сам по `data/*.parquet`.
   Чужая статистика может устареть относительно данных.
4. **Пакет — недоверенный вход.** Он может прийти файлом откуда угодно. Валидация по JSON Schema,
   запрет исполняемой сериализации, лимиты размера, нормализация путей.
5. **Пакет работает offline.** Для чтения не нужна ни работающая DataArena, ни сеть.
   Все поля `links` — необязательная навигация, а не зависимость.
6. **Неизвестные optional-поля игнорируются.** Потребитель обязан прочитать пакет, собранный
   более новой minor-версией, не падая на незнакомых полях.
7. **Breaking change → новая major-версия.** Потребитель отвергает неизвестную major-версию
   с внятным сообщением, а не пытается угадать.

## A. Дерево пакета

```
<name>.dapkg/                     каталог; для передачи одним файлом — <name>.dapkg.zip
├── manifest.json                 ОБЯЗАТЕЛЕН. Единственная точка входа
├── data/
│   ├── part-0000.parquet         ОБЯЗАТЕЛЕН, минимум одна часть
│   └── part-0001.parquet
├── schema.json                   опционален
├── profile.json                  опционален
├── lineage.json                  опционален
└── recipe.json                   опционален
```

**Больше в пакете не должно быть ничего.** Файл, не перечисленный в `manifest.parts`
и не входящий в `manifest.data.files`, потребитель игнорирует и не читает.

### Порядок строк — нормативен

Части собираются в одну таблицу в порядке `manifest.data.files`; строки внутри части —
в порядке их хранения в Parquet. Позиция строки в собранной таблице, начиная с нуля, —
**канонический `row_index`**. На него ссылаются `profile.findings[].drilldown` и любые
указания на конкретные строки.

Без этого правила «17 выбросов в строках 183, 402, …» означало бы разные строки у producer
и consumer, и — что важнее — **не воспроизводился бы сам fingerprint**: он зависит от порядка
строк. Схемы `part-NNNN` обязаны совпадать во всех частях.

### `row_key` — устойчивая ссылка вместо позиции

Позиция строки нормативна внутри одной версии пакета, но она **сдвигается при перепаковке**,
а ссылка на неё при этом остаётся внешне валидной и указывает не туда. Поэтому для ссылок,
которые переживают перепаковку, есть необязательное поле:

```json
"data": { "row_key": ["customer_id"] }
```

`row_key` — колонки, уникально идентифицирующие строку. Если producer его указал, потребитель
использует именно его для устойчивых ссылок, а позицию — только внутри одной прочитанной версии.
Если `row_key` нет, остаётся только позиция, и ссылки не переживают перепаковку — это ограничение,
о котором потребитель обязан знать.

Машиночитаемые схемы лежат рядом и являются частью контракта:

| Файл | Схема |
|---|---|
| `manifest.json` | [`schema/manifest.schema.json`](schema/manifest.schema.json) |
| `schema.json` | [`schema/schema.schema.json`](schema/schema.schema.json) |

Все схемы — JSON Schema draft 2020-12, `"additionalProperties": true` на верхних уровнях
(правило 6), `"additionalProperties": false` внутри строго перечислимых структур.

Обе стороны валидируют пакет этими схемами в тестах. Схемы в двух репозиториях обязаны быть
побайтово идентичными; расхождение — ошибка CI.

## D. Fingerprint: алгоритм и что входит в хеш

Контракт использует **два разных хеша с разным назначением**. Их путаница — источник ошибок,
поэтому разделение нормативно.

| | `parts[].sha256` | `data.content_fingerprint` |
|---|---|---|
| Что хеширует | байты конкретного файла | значения таблицы |
| Назначение | целостность, обнаружение подмены и порчи | идентичность данных, дедупликация, lineage |
| Зависит от формата хранения | да | **нет** |
| Переживает перезапись файла | нет | да |
| Стоимость на 1M×7 | ~0.02 с | 0.36 с (измерено) |

`parts[].sha256` — обычный SHA-256 байтов файла, `hex`, нижний регистр.

### `dataarena-logical-sha256-v1`

Отпечаток описывает **логическое содержимое** датасета и считается по значениям, а не по байтам
файла. Обязательное свойство: потребитель должен уметь пересчитать его по прочитанному
`data/*.parquet` и получить то же число, не импортируя код DataArena.

**Входит в хеш:** идентификатор алгоритма, число строк, число колонок, порядок колонок,
имена колонок, логические типы, позиции пропусков, канонические представления значений,
порядок строк.

**Не входит в хеш:** версия любой библиотеки, метаданные writer, сжатие, dictionary encoding,
раскладка row group в Parquet, метаданные файловой системы, произвольный `custom_metadata`.
Именно поэтому одни и те же данные в Parquet, Arrow IPC и CSV дают один отпечаток.

> **Почему не хеш Arrow IPC.** Первая версия алгоритма хешировала канонический Arrow IPC-поток,
> и обе стороны её приняли. Проверка показала, что он **не переживает round-trip через Parquet**:
> те же данные после записи в Parquet и обратного чтения дают другие байты IPC. Значит потребитель
> физически не смог бы пересчитать отпечаток, а жёсткий отказ по несовпадению срабатывал бы
> на каждом импорте, и виноват был бы не пакет. Алгоритм заменён на логическую канонизацию.

### Вход алгоритма — нормативно

**Вход отпечатка — таблица, прочитанная из `data/*.parquet`**, и только она:

- части читаются и конкатенируются в порядке `manifest.data.files`;
- строки внутри части — в порядке хранения в Parquet;
- **порядок колонок и их типы берутся из Parquet**;
- `schema.json` **не является входом отпечатка** ни в какой части.

Последнее правило существует по двум причинам. Во-первых, `schema.json` необязателен:
`negative/minimal.dapkg` объявляет отпечаток и схемы не содержит вовсе — по правилу
«источник — схема» его нечем было бы проверить. Во-вторых, единственный источник снимает
сам вопрос «кто главнее» и делает отпечаток детерминированным.

Это правило работает в паре с запретом расхождения (см. ниже): в валидном пакете
`schema.json` и Parquet физически не могут описывать разные данные, поэтому выбор источника
ни на что не влияет — он зафиксирован только ради однозначности реализации.

### Расхождение `schema.json` с данными — пакет невалиден

Если `schema.json` присутствует, он обязан описывать ровно то, что лежит в Parquet:

| Что сверяется | Правило |
|---|---|
| Имена колонок и их порядок | обязаны совпадать с Parquet точно |
| `logical_type` каждой колонки | обязан совпадать с выведенным из Parquet по таблице ниже |
| `position` | обязана совпадать с фактической позицией |

Любое расхождение — **отказ**, код `package_schema_mismatch`. Формулировки «выигрывает
Parquet» в контракте нет: пакет, где описание не соответствует данным, не должен читаться
вообще, потому что дальше на это описание опираются и потребитель, и человек.

`physical_type` при этом информативен и не сверяется: `Int32` и `Int64` дают один
`logical_type`, а ширина в отпечаток не входит.

### Отображение физического типа в `logical_type` — нормативно

Реализатор не должен угадывать соответствие. Таблица полна: тип, которого в ней нет,
**обязан быть ошибкой сборки пакета**, а не приводиться к строке.

| Физический тип Parquet / Polars | `logical_type` |
|---|---|
| `Boolean` | `boolean` |
| `Int8`, `Int16`, `Int32`, `Int64`, `UInt8`, `UInt16`, `UInt32`, `UInt64` | `integer` |
| `Float32`, `Float64` | `float` |
| `Decimal(p, s)` | `decimal` |
| `Date` | `date` |
| `Datetime(любая единица, любая зона)` | `datetime` |
| `Duration(любая единица)` | `duration` |
| `Time` | `time` |
| `String` / `Utf8` | `string` |
| `Binary` | `binary` |
| **любой другой** (`Categorical`, `Enum`, `List`, `Struct`, `Null`, …) | **ошибка сборки пакета** |

Причина запрета вместо тихого приведения: `Categorical`, `List` и `Struct` пришлось бы
хешировать через строковое представление библиотеки, которое между версиями не гарантировано.
Producer обязан привести такую колонку к поддерживаемому типу до сборки пакета и сказать
об этом пользователю.

```
digest = SHA-256 поток:

  "dataarena-logical-sha256-v1" || 0x0A
  ascii(row_count) || 0x1E
  ascii(column_count) || 0x1D

  для каждой колонки, в порядке колонок Parquet:
      uint32_le(len(utf8(name))) || utf8(name)
      ascii(logical_type) || 0x1E
      SHA-256(null_mask_bytes)      (32 байта)
      SHA-256(value_bytes)          (32 байта)
      0x1D

fingerprint = hex(digest)          // нижний регистр, 64 символа
```

**`logical_type`** — одно из: `boolean`, `integer`, `float`, `decimal`, `date`, `datetime`,
`duration`, `time`, `string`, `binary`. Физическая ширина в хеш не входит: `Int32` и `Int64` с теми же
значениями дают один отпечаток.

**`null_mask_bytes`** — битовая маска пропусков, по одному биту на строку, порядок бит
внутри байта — little-endian (`numpy.packbits(..., bitorder="little")`), хвост последнего
байта дополняется нулями.

**`value_bytes`** — значения колонки подряд, все целочисленные представления little-endian.
Пропуски заменяются нейтральным значением, потому что сам факт пропуска уже учтён маской:

| `logical_type` | Кодирование | Значение вместо null |
|---|---|---|
| `integer` | `int64` LE | `0` |
| `float` | `float64` LE, битовое представление | `0.0` |
| `decimal` | десятичная строка с нормализованным масштабом, длина + ASCII | пустая строка |
| `boolean` | `uint8`, `0` / `1` | `0` |
| `date` | `int32` LE, дней от 1970-01-01 | `0` |
| `datetime` | `int64` LE, микросекунд от 1970-01-01T00:00:00Z | `0` |
| `duration` | `int64` LE, микросекунд | `0` |
| `time` | `int64` LE, наносекунд от полуночи | `0` |
| `string` | блок `uint32` LE длин всех значений, затем UTF-8 байты подряд | пустая строка (длина 0) |
| `binary` | так же, но байты как есть | пустой blob (длина 0) |

### Обязательные нормализации

Без них отпечаток зависел бы от способа получения значения, а не от самого значения.

| Что | Правило | Проверено |
|---|---|---|
| NaN | все варианты сводятся к quiet NaN `0x7FF8000000000000` | ✅ |
| Минус ноль | `-0.0` → `0.0`: по IEEE-754 они равны | ✅ |
| Ширина целого | не входит в хеш: `Int32` и `Int64` с теми же значениями — один датасет | ✅ |
| Ширина float | `Float32` расширяется до `Float64`; расширение точное, ложных совпадений не даёт | ✅ |
| Decimal | масштаб нормализуется: `1.50` и `1.5` — одно число. Float не используется, точность не теряется | ✅ |
| Datetime | приводится к UTC, разрешение к микросекундам; наивные значения считаются UTC | ✅ |
| Строки | **Unicode NFC**: «café» одним кодовым пунктом и «cafe» + комбинирующий акцент выглядят одинаково и обязаны давать один отпечаток. NFC применяется и к **именам колонок** | ✅ |
| Пустая строка и null | различаются: полезная нагрузка у обоих пуста, но факт пропуска несёт отдельно хешируемая маска | ✅ |

### Почему поток нельзя прочитать двояко

Значения переменной длины кодируются **блоком длин перед полезной нагрузкой**, а не разделителями.
Поэтому `["ab", "c"]` даёт длины `[2, 1]`, а `["a", "bc"]` — `[1, 2]`: склейка `"abc"` одинакова,
а отпечаток разный. Типы фиксированной ширины неоднозначности не создают по построению.

### Решение о параллельном вычислении

Рассматривался вариант «хеш каждой части независимо, итог = `sha256(header || h(part0) || h(part1))`».
**Отклонён для v1.** Причина: выбранная поколоночная схема уже даёт 0.79 с на 1 000 000 × 7,
и усложнять форму алгоритма ради скорости, которой хватает, нет оснований. Если на реальных
широких датасетах это станет узким местом — это будет `dataarena-logical-sha256-v2`
с явной сменой `algorithm`, а не тихое изменение v1.

### Воспроизводимость между версиями библиотек — проверена

Утверждение «воспроизводимо независимо от версии библиотек» без прогона остаётся утверждением.
Прогон выполнен: `reference/check_reproducibility.py` пересчитывает отпечаток golden package
и сверяет с манифестом.

| Окружение | Отпечаток golden package | |
|---|---|---|
| Polars 1.44.1 (версия сборки) | `457184a0…16adac3` | ✅ совпал |
| Polars 1.20.0 (независимая) | `457184a0…16adac3` | ✅ совпал |

Скрипт обязан входить в CI обеих сторон и запускаться минимум на двух версиях Polars.

### Что делать при расхождении

| Расхождение | Реакция потребителя |
|---|---|
| `parts[].sha256` не сошёлся | **Жёсткий отказ.** Данные не читаются вообще |
| `content_fingerprint` не сошёлся при пересчёте | **Жёсткий отказ.** Пакет внутренне противоречив |
| `content_fingerprint.algorithm` незнаком | **Отказ по умолчанию.** Приём допустим только по явному действию пользователя, и тогда снимок обязан нести видимый признак `fingerprint_verified: false` |

Мягкая реакция на несовпадение отпечатка запрещена: пакет, где манифест не описывает
собственные данные, нельзя использовать для воспроизводимого эксперимента.

Незнакомый алгоритм тоже не является мягким случаем. Иначе это путь понижения: пакет,
объявивший `algorithm: "чтоугодно/9"`, прошёл бы **без** проверки содержимого, тогда как
несовпадение известного алгоритма — жёсткий отказ. Приём непроверяемого пакета возможен
только как осознанное действие пользователя и обязан быть видимым на всём, что из него
построено.

## E. Правила версионирования

`format_version` — строка **semver** `MAJOR.MINOR.PATCH`.

| Изменение | Версия | Совместимость |
|---|---|---|
| Уточнение текста спецификации, не меняющее данные | PATCH | полная |
| Добавлено **необязательное** поле | MINOR | вперёд и назад |
| Добавлена новая **необязательная** часть пакета | MINOR | вперёд и назад |
| Расширен список допустимых значений enum | MINOR | назад — да; вперёд — потребитель обязан игнорировать неизвестное значение |
| Поле стало обязательным | **MAJOR** | нет |
| Изменена семантика существующего поля | **MAJOR** | нет |
| Поле удалено или переименовано | **MAJOR** | нет |
| Изменён алгоритм fingerprint | новый `algorithm` id, **не** новая версия пакета | сосуществуют |

### Что меняет версию, а что нет

Таблица выше отвечает на вопрос «какая часть версии». Этот раздел отвечает на предыдущий:
**меняется ли версия вообще**. Без него разница между «тегом» и «main» растёт по одной
безобидной правке за раз, и через месяц тег перестаёт описывать main — причём никто
не замечает момента, когда это произошло.

| Что изменилось | Версия | Что обязано произойти |
|---|---|---|
| Пояснение, обоснование, журнал решений, правило управления изменениями | не меняется | — |
| Переформулировка нормативного требования **без изменения смысла** | PATCH | обе стороны перечитывают |
| Нормативное требование, JSON Schema, фикстура, эталонная реализация, алгоритм отпечатка | **минимум PATCH**, при несовместимости MAJOR | пересборка golden package, прогон матрицы обеими сторонами, **перенос тега** |

При расхождении тега и `main`:

- **тег** авторитетен для реализаций: по нему сверяются producer и consumer;
- **`main`** авторитетен для чтения человеком;
- **нормативное расхождение тега и `main` — дефект, а не состояние.**

### Версионированное событие — это изменение поведения, а не правка файла

Правило выше говорит про «эталонную реализацию» и читается как «любая правка в `reference/`».
Это слишком широко, и первое же применение дало ложное срабатывание: добавление
`reference/run_matrix.py` — прогонщика, который ничего не решает, а только вызывает уже
существующие проверки, — по букве требовало пересборки golden package и переноса тега.

Уточнение: **версию двигает изменение поведения контракта, а не факт правки файла в каталоге.**

| Изменение в `reference/` | Версия |
|---|---|
| Новый вспомогательный инструмент: прогонщик, сборщик фикстур, проверка воспроизводимости | не меняется, **если** нормативные модули не менялись и матрица даёт прежний результат |
| Любая правка `fingerprint.py`, `validate_package.py` или логики сборки пакета | минимум PATCH со всей процедурой |

Оба условия в первой строке проверяются **запуском, а не на глаз**: сверкой нормативных
модулей между тегом и `main` и прогоном матрицы. Пример такой проверки — в §J.

Причина уточнения та же, по которой владелец не стал приводить `reference/` к стилю линтера:
**правило, требующее церемонии там, где риска нет, перестают соблюдать целиком** — сначала
в мелочи, потом везде. Дешевле сузить правило до реального риска, чем терпеть его
регулярное нарушение.

Уточнение предложено потребителем на разборе собственного ложного срабатывания.

Правило действует и на владельца контракта. Именно поэтому эталонные реализации
в [`reference/`](reference/) **не подвергаются автоматическому форматированию и линтингу**:
их изменение — версионированное событие, а не побочный эффект запуска инструмента на чьей-то
машине. Их корректность стережёт матрица из 14 фикстур и проверка воспроизводимости
на разных версиях библиотеки — это более сильное свидетельство, чем соответствие стилю.

Зафиксировано владельцем контракта; на стороне ModelArena — решение D-17.

### Отпечаток — самостоятельный версионированный протокол

`content_fingerprint.algorithm` версионируется **независимо** от `format_version` и живёт
по более строгому правилу:

> **После freeze семантика внутри идентификатора алгоритма не меняется никогда.**

Даже если найдётся более удачная канонизация decimal, datetime или Unicode — это **новый
идентификатор** (`dataarena-logical-sha256-v2`), а не правка существующего. Ни при каких
обстоятельствах, включая исправление того, что выглядит как ошибка.

Причина в том, чем является отпечаток. Это не хеш файла, а **записанная идентичность
датасета**: она попадает в карточки экспериментов и в артефакты обученных моделей и живёт
там годами. Смена семантики под тем же именем означает, что все ранее сохранённые отпечатки
начинают означать что-то другое: старые эксперименты перестают сходиться со своими данными,
а выглядит это для пользователя как «пакет битый» — то есть ошибка проявляется далеко
от места, где её внесли, и указывает не на ту причину.

Сосуществование версий алгоритма стоит дёшево: потребитель, встретивший незнакомый
идентификатор, отказывается понятным образом (§D), а не гадает.

Зафиксировано владельцем контракта; на стороне ModelArena — решение D-16.

Правила чтения версии потребителем:

- `major != 1` → отказ с текстом, какие версии понимаются;
- `minor` выше своей → читать, незнакомые поля игнорировать, в `warnings` записать,
  что пакет собран более новой minor-версией;
- `patch` не влияет на поведение.

Спецификация и golden package помечаются одним тегом в обоих репозиториях:
`contract/dataset-package-v1.0.0`.

## H. Матрица валидации

### Лимиты

Лимиты разделены на две группы, и это разделение принципиально.

**Метаданные — лимиты в контракте.** JSON разбирается в память целиком **до** любой проверки,
поэтому предел должен быть известен заранее и одинаков у всех потребителей.

| Параметр | Предел | Причина |
|---|---|---|
| `manifest.json` | 1 MiB | читается первым, до любых проверок |
| Каждый из `schema.json`, `profile.json`, `lineage.json`, `recipe.json` | 16 MiB | разбор в память |
| Все метаданные суммарно | 64 MiB | |
| Число файлов в архиве | 10 000 | zip-бомба |
| Отношение распакованного к сжатому | 100 : 1 | zip-бомба |
| Вложенные архивы | **запрещены** | рекурсивная распаковка обходит любой лимит |
| Число частей данных | 4 096 | |
| Глубина вложенности JSON | 32 | защита разбора |

**Данные — лимита в контракте нет.** Он конфигурируется потребителем: датасет на 50 ГБ
не является некорректным пакетом, он просто может не поместиться у конкретного потребителя.
Жёсткое число в контракте сделало бы легитимные пакеты формально невалидными.

| Параметр | Где задаётся | Умолчание |
|---|---|---|
| Суммарный размер `data/*.parquet` | конфигурация потребителя | 5 GiB |

Потребитель, отказавший по своему лимиту, обязан сказать, что это **его** ограничение,
а не дефект пакета.

### Golden package и негативные фикстуры

В [`golden/`](golden/) — эталонный пакет, побайтово одинаковый в обоих репозиториях.
Он источник истины: изменение формата, ломающее golden package, обязано сопровождаться
повышением версии.

Состав эталонного пакета:

- две части данных — проверка сборки из нескольких файлов;
- колонки всех `semantic_type`: `id`, `numeric`, `categorical`, `datetime`, `boolean`, `text`;
- пропуски минимум в двух колонках;
- одна колонка высокой кардинальности;
- `hints.suggested_targets` с двумя кандидатами разной `confidence`.

Позитивные фикстуры:

| Фикстура | Что проверяет |
|---|---|
| `customers_golden.dapkg` | полный валидный пакет, две части данных |
| `negative/minimal.dapkg` | только `manifest.json` + одна часть — опциональное действительно опционально |
| `negative/future-minor.dapkg` | `format_version: "1.7.0"` + незнакомые поля → чтение с warning |
| `negative/sampled-profile.dapkg` | `sampled: true` → чтение + плашка в UI |

Негативные фикстуры в [`golden/negative/`](golden/negative/):

| Фикстура | Что проверяет | Ожидаемый код |
|---|---|---|
| `future-major.dapkg` | `format_version: "2.0.0"` | `package_version_unsupported` |
| `corrupted-part.dapkg` | испорченный `sha256` части | `package_integrity_failed` |
| `fingerprint-mismatch.dapkg` | подменённые данные при **верных** `sha256` | `package_fingerprint_mismatch` |
| `malformed-schema.dapkg` | `schema.json` нарушает JSON Schema | `package_part_invalid` |

## I. Конфликтные места двух предложений и принятое решение

Сведены предложения DataArena и ModelArena (`ARCHITECTURE_REVIEW.md` §6).
Решение по каждому пункту принято и зафиксировано.

| # | Вопрос | DataArena предлагала | ModelArena предлагала | **Решение** | Почему |
|---|---|---|---|---|---|
| 1 | Имя манифеста | `manifest.json` | `package.json` | **`manifest.json`** | `package.json` однозначно читается как npm-манифест |
| 2 | Тип версии | semver-строка | целое число | **semver-строка** | нужны minor-изменения без слома совместимости |
| 3 | Файл данных | несколько частей | одна `data.parquet` | **массив частей** | одна таблица не переживёт крупный датасет; массив из одного элемента — норма |
| 4 | Схема | отдельный `schema.json` | массив в манифесте | **отдельный файл** | манифест читается первым; схема на 200 колонок его раздувает |
| 5 | Профиль | по сути обязателен | опционален | **опционален** | потребитель всё равно пересчитывает |
| 6 | Рецепт | отдельный `recipe.json` | внутри `lineage.json` | **отдельный** | рецепт применяют к новым файлам, lineage только читают |

## J. Критерий freeze

Спецификация находится в статусе **release candidate**. Формат считается замороженным
только при одновременном выполнении:

| # | Условие | Состояние |
|---|---|---|
| J-1 | Спецификация полна: §A–§I заполнены | ✅ |
| J-2 | JSON Schema покрывают все пять файлов пакета | ✅ |
| J-3 | Golden package и все фикстуры собраны | ✅ |
| J-4 | **Producer-проверки DataArena проходят** на этом golden package | ✅ |
| J-5 | **Consumer-проверки ModelArena проходят** на **том же** наборе фикстур | ✅ 14 из 14 |
| J-6 | Отпечаток воспроизведён на **двух разных версиях** Polars | ✅ 1.20.0, 1.43.0, 1.44.1 |

**Все шесть условий выполнены. Формат заморожен 2026-09-06.**

Следствия:

- `format_version` зафиксирована обеими сторонами;
- breaking-изменения — только через следующую major-версию;
- Stage 1 идёт параллельно на обеих сторонах;
- тег `contract/dataset-package-v1.0.0` стоит в обоих репозиториях и указывает
  на одно и то же содержание каталога.

Кросс-проверка ведётся на **одном и том же** каталоге `golden/`: он побайтово идентичен
в двух репозиториях, поэтому «тот же пакет» — проверяемое утверждение, а не договорённость.

### Как проверить, разошёлся ли тег с `main`

Сверяются деревья нормативных частей, а не файлы глазами:

```bash
git diff --stat contract/dataset-package-v1.0.0 main -- docs/contracts
git rev-parse contract/dataset-package-v1.0.0:docs/contracts/schema  main:docs/contracts/schema
git rev-parse contract/dataset-package-v1.0.0:docs/contracts/golden  main:docs/contracts/golden
python docs/contracts/reference/run_matrix.py docs/contracts
```

Совпадение хешей деревьев `schema/` и `golden/` плюс PASS матрицы означает, что расхождение
не нормативное. Проверено 2026-09-06: между тегом и `main` изменены только README,
спецификация и добавлен `run_matrix.py`; `fingerprint.py`, `validate_package.py`,
`build_golden.py`, `schema/` и `golden/` побайтово идентичны.

### Что засчитывается за J-5

PASS засчитывается **только от реализации, написанной по этому документу**, без импорта
и без чтения `reference/*.py`. Эталон, запущенный дважды, — это одна реализация, а не две:
именно поэтому первая по-настоящему независимая проверка сразу дала два блокирующих дефекта
текста (§I, строки 32–33).

Отчёты потребителя лежат на его стороне и в зеркалирование не входят:
[CONSUMER_VERIFICATION.md](https://github.com/forit-tech/ModelArena/blob/main/docs/contracts/CONSUMER_VERIFICATION.md),
реализация — `tests/contracts/`.

**Как J-5 было закрыто.** Владелец контракта взял независимую реализацию потребителя
(`ModelArena/tests/contracts/consumer_check.py`) и запустил её **на своём каталоге**,
а не принял отчёт на словах. Результат — все 14 фикстур повели себя ровно так, как обещает
таблица §H, и на Polars 1.20.0, и на 1.44.1. Отпечаток golden package
`457184a0a0dc0377…` воспроизведён независимой реализацией на трёх версиях библиотеки.

Такой порядок проверки обязателен и для будущих ревизий: прогон чужого кода на своём
наборе фикстур занимает минуту и заменяет несколько обменов отчётами, которые успевают
устареть между отправкой и прочтением.

**Почему эталона недостаточно.** Три ревизии формата до freeze вызваны находками
потребителя, и ни одна не всплыла бы при проверке эталона эталоном. Причина не в том,
что эталон плох, а в том, что **эталон и спецификация — не два независимых свидетеля**:
их писал один автор, читая один и тот же замысел. Прогон эталона подтверждает внутреннюю
согласованность кода, но не то, что документ описывает этот код. Расхождение текста и кода
ловится только реализацией, написанной по тексту.

Отсюда процедурное следствие: PASS засчитывается от реализации по документу, а найденное
расхождение присылается **списком владельцу**, а не устраняется подгонкой своей реализации
под чужой код. Подгонка закрывает симптом и оставляет дефект в тексте, по которому будет
писать следующий.

## Схема — `schema.json`

```json
{
  "format_version": "1.0.0",
  "columns": [
    {
      "name": "customer_id",
      "position": 0,
      "physical_type": "Int64",
      "logical_type": "integer",
      "semantic_type": "id",
      "nullable": false,
      "unique": true,
      "description": null,
      "source": { "dataset": "users.csv", "original_name": "userid" }
    }
  ],
  "primary_key": ["customer_id"],
  "constraints": [
    { "kind": "not_null", "columns": ["customer_id", "plan"] },
    { "kind": "unique",   "columns": ["customer_id"] }
  ]
}
```

Три уровня типа отвечают на разные вопросы и не дублируют друг друга:

| Уровень | Вопрос | Значения |
|---|---|---|
| `physical_type` | как хранится в Parquet | `Int64`, `Float64`, `String`, `Date`, … |
| `logical_type` | какой это тип данных | `boolean`, `integer`, `float`, `date`, `datetime`, `duration`, `time`, `string`, `binary` |
| `semantic_type` | что это значит | `id`, `numeric`, `categorical`, `datetime`, `boolean`, `text` |

`logical_type` — тот же список, что входит в fingerprint (§D). `semantic_type` — то, ради чего
потребитель читает схему: он определяет, кодировать колонку, масштабировать, разворачивать
в календарные признаки или исключить.

Имена колонок, их порядок и `logical_type` обязаны совпадать с Parquet: расхождение делает
пакет невалидным (§D, `package_schema_mismatch`). `physical_type` информативен и не сверяется.

## Профиль — `profile.json`

Структура и пример — в [`examples/profile.json`](examples/profile.json). Ключевые элементы:

- `computed_at`, `computed_on: { rows, sampled }` — если профиль считался по выборке,
  `sampled: true` обязателен;
- `dataset` — сводные счётчики и `quality_breakdown` с объяснением каждого штрафа;
- `columns[]` — статистики, гистограммы, частые значения, примеры;
- `correlation` — метод, матрица, `high_pairs`;
- `findings[]` — находка с полями `kind`, `severity`, `column`, `count`, `method`, `threshold`,
  `explanation` и `drilldown`;
- `suspicious_columns[]` — колонка, причина, рекомендация. **Без слова leakage.**

`findings[].drilldown` — исполняемый запрос, а не описание:

```json
{
  "kind": "sql",
  "dialect": "duckdb",
  "query": "SELECT * FROM dataset WHERE monthly_spend > 1410.0 OR monthly_spend < -510.0",
  "row_indexes": [183, 402, 1177]
}
```

`row_indexes` — канонические позиции строк (§A). Потребитель **не исполняет** `query`:
это ссылка для DataArena; для показа строк он использует `row_indexes`.

## Lineage — `lineage.json`

`sources[]` — исходные файлы с `sha256`, размером, числом строк и опциями чтения.
`graph[]` — узлы `{id, op, inputs, output_rows, params}`.
`row_count_trace[]` — как менялось число строк по шагам.

Это **не Git для датасетов**: ветвлений, слияний версий и diff-ов нет, только линейная
история происхождения одного результата.

## Рецепт — `recipe.json`

`inputs[]` с `alias`, `required_columns`, `format_hint`, `source_sha256`; `steps[]`; `output`.

`source_sha256` фиксирует, на каких файлах рецепт был получен. При повторном применении
к новым версиям файлов хеши не совпадут — и producer обязан **сказать об этом**, а не молча
выполнить рецепт на других данных. `required_columns` проверяются до выполнения.

Потребитель `recipe.json` **не исполняет** — только показывает.

## Транспорт

| Способ | Описание |
|---|---|
| Каталог | `<name>.dapkg/` на диске |
| Архив | `<name>.dapkg.zip`, тот же состав; лимиты §H |
| Pull | producer отдаёт `package_url`, consumer скачивает сам, по явному действию пользователя, только http/https, редиректы на файловые схемы запрещены |
| API producer | `GET /api/workspaces/{ws}/packages/{package_id}` → манифест; `GET …/download` → `.dapkg.zip` |
| Deep link | `Open in ModelArena` ведёт на фронт consumer с `package_url`; передаётся **ссылка, а не данные** |

Если consumer недоступен — producer сообщает об этом и продолжает работать.
Если producer недоступен — уже скачанный пакет читается полностью (правило 5).

## Что в контракт сознательно не входит

| Не входит | Почему |
|---|---|
| train/test split | решение потребителя, зависит от задачи и стратегии валидации |
| scaling, encoding под модель | часть ML-пайплайна, не данных |
| выбранный target | producer предлагает кандидатов в `hints`, выбирает человек |
| ML-метрики | не существуют на этапе подготовки данных |
| артефакты модели | обратное направление, забота потребителя |
| вердикт о leakage со стороны producer | без target необоснован (§G) |
| исполняемый код в любом виде | правило 4 |
