**Проблема:** контракт DataArena ↔ ModelArena был спроектирован **дважды и независимо** —
в этой сессии ([dataset-package-v1.md](dataset-package-v1.md)) и в параллельной сессии
ModelArena ([ModelArena/docs/ARCHITECTURE_REVIEW.md](https://github.com/forit-tech/ModelArena/blob/main/docs/ARCHITECTURE_REVIEW.md), §6).

> ## ✅ РАЗРЕШЕНО 2026-09-06
>
> Обе стороны согласовали единую версию. Итог — в
> [dataset-package-v1.md](dataset-package-v1.md) 1.0.0, решение по каждому спорному пункту
> сведено там в таблицу §I. Владелец контракта — DataArena; обязательства потребителя —

Оба предложения датированы 2026-09-06.

Хорошая новость: предложения не противоречат друг другу по смыслу. Расходятся имена файлов,
структура и несколько существенных правил — то есть склеить их можно без переделки идеи.

## 1. Таблица расхождений

| Аспект | DataArena (это предложение) | ModelArena (параллельное) | Рекомендация |
|---|---|---|---|
| Имя манифеста | `manifest.json` | `package.json` | **`manifest.json`** — `package.json` в экосистеме однозначно читается как npm |
| Тип версии | `"1.0"` (semver-строка) | `1` (целое) | **semver-строка** — нужны minor-изменения без слома совместимости |
| Файл данных | `data/part-NNNN.parquet`, разбиение | `data.parquet`, одна таблица | **части**, но `parts` из одного элемента — норма. Одна таблица не переживёт крупный датасет |
| Схема | отдельный `schema.json` | массив внутри манифеста | **отдельный файл** — схема на 200 колонок раздувает манифест, который читается первым |
| Профиль | `profile.json` | `profile.json`, опционален | **опционален** — версия ModelArena правильнее |
| Рецепт | отдельный `recipe.json` | внутри `lineage.json` | **отдельный** — рецепт применяют к новым файлам, lineage только читают |
| Хеш | `sha256` на каждую часть | `fingerprint_sha256` на датасет | **оба**: на части — для проверки целостности, на датасет — для сверки идентичности |
| Версия датасета | нет | `version: {dataset_id, version, parent_version}` | **взять из ModelArena** — нужного поля у меня не было |
| `hints` | список кандидатов с `confidence` | `suggested_target` / `group` / `time` + `excluded_candidates` | **склеить**: список кандидатов с причиной + отдельные подсказки group/time |
| Транспорт | `GET /packages/{id}/download` | pull по `package_url` + multipart import | **взять из ModelArena** — pull-модель развязывает сервисы |
| Обратные ссылки | нет | `links.inspect_url_template` | **взять из ModelArena** — «показать эту колонку в DataArena» полезно |
| Findings с `drilldown` | есть, исполняемый SQL | нет | **оставить** |
| `row_count_trace` | есть | нет | **оставить** — отвечает на вопрос «где выросли строки» |
| `sampled: true` | есть | нет | **оставить** — иначе приблизительные статистики выдаются за точные |
| `required_columns` в рецепте | есть | нет | **оставить** — проверка до выполнения, а не падение в середине |
| Golden package | предложен | не упомянут | **оставить** — единственный надёжный способ не разъехаться |

## 2. Правила, которые надо взять из версии ModelArena целиком

Три пункта в их предложении сформулированы лучше, и это не вопрос вкуса:

**2.1. `hints` и `profile.json` — advisory; ModelArena пересчитывает все числа сама.**

> «Чужая статистика может устареть относительно данных.»

Это правильнее моей формулировки. Профиль в пакете — способ не считать заново *для показа*,
но любое решение (readiness, leakage, выбор стратегии) должно опираться на пересчёт
по `data.parquet`. Иначе ошибка в профиле DataArena тихо распространяется на ML-решения.

**2.2. Пакет — недоверенный вход.**

> «Валидация по JSON Schema, никаких pickle/joblib внутри, никакого eval выражений, лимит размера.»

У меня этого не было вовсе. Пакет может прийти файлом откуда угодно — запрет на исполняемую
сериализацию внутри обязателен.

**2.3. Pull вместо push.**

ModelArena сама скачивает пакет по URL. DataArena не должна знать про очереди и авторизацию
ModelArena — только про её base URL.

## 3. Расхождение по границе продукта

В §3 их документа граница описана так же, как в моём
[MIGRATION_MAP](https://github.com/forit-tech/DataArena/blob/main/docs/MIGRATION_MAP.md) и [ModelArena/docs/SCOPE.md](https://github.com/forit-tech/ModelArena/blob/main/docs/SCOPE.md).
Содержательных противоречий нет.

Одно уточнение, которое стоит зафиксировать явно: **кто считает leakage.**
В моём предложении DataArena отдаёт `suspicious_columns` с причиной, но не утверждает leakage
(без target утверждение необоснованно). В их §12 есть Leakage Guard на стороне ModelArena.
Это согласуется: DataArena — подозрения без target, ModelArena — проверка после выбора target.
Конфликта нет, но обе стороны должны описывать это одинаково, чтобы пользователь не видел
два разных вердикта об одной колонке.

## 4. Что было сделано

1. ✅ Владельцем контракта назначена DataArena — формат описывается там, где производится.
   ModelArena держит побайтовую копию каталога и документ обязательств потребителя.
2. ✅ Собрана объединённая версия 1.0.0: структура, findings и drilldown — из предложения
   DataArena; правила безопасности, транспорт, версионирование датасета и `links` — из
   предложения ModelArena. Решение по каждому пункту — в §I спецификации.
3. ✅ Golden package и шесть негативных фикстур собраны, лежат в обоих репозиториях
   и проходят валидацию собственными JSON Schema.
4. ✅ Ни одна сторона не реализовывала импорт/экспорт до фиксации версии.

**Найдено при сведении, чего не было ни в одном из двух предложений:**

- отпечаток на основе Arrow IPC **не переживает round-trip через Parquet** — потребитель не смог
  бы его пересчитать. Алгоритм заменён на канонизацию уровня значений и проверен на восьми свойствах;
- порядок строк не был зафиксирован ни у кого, а без него `drilldown` указывает на разные
  строки у producer и consumer. Теперь нормативен;
- лимиты размера были названы словами без чисел. Числа зафиксированы.

## 5. Замечание о параллельной работе

Две сессии независимо спроектировали один и тот же контракт — это дублирование, которое
обошлось дёшево сейчас и обойдётся дорого, если то же произойдёт с кодом.

Практическое предложение: разделить владение по артефактам, а не только по репозиториям.
Контракт, golden package и правила версионирования — у одной стороны; вторая сверяется с ними
и присылает замечания.

Отдельно: в этой сессии в ModelArena были созданы `README.md` и `docs/SCOPE.md`.
Они не перезаписали ничего из работы параллельной сессии, но частично дублируют
§3 её документа. Если ModelArena ведёт другая сессия — эти два файла стоит либо
отдать ей на владение, либо удалить в пользу её версии.
