# План реализации DataArena

Этапы идут в порядке, при котором **каждый следующий опирается на уже работающий предыдущий**,
и после каждого инструментом можно пользоваться — пусть и в меньшем объёме.

## Definition of Done — общее правило

Этап закрыт, только если выполнено всё:

1. backend реализован, не заглушка;
2. frontend вызывает реальный backend, никаких кнопок без действия;
3. состояние сохраняется там, где это обещано интерфейсом;
4. ошибки обработаны и показаны понятным текстом;
5. есть тесты: unit на логику, integration на сценарий;
6. сценарий пройден руками в браузере;
7. `pytest`, `ruff`, `mypy`, `eslint`, `tsc`, `vitest`, `npm run build` — зелёные;
8. README отражает то, что реально работает, без обещаний;
9. git commit + короткий checkpoint с фактами: что сделано, что измерено, что не сделано.

## Этап 0.5 — Контракт с ModelArena ✅ FROZEN

Вынесен вперёд относительно первоначального плана (был Этапом 10). Причина: контракт —
единственное, что при расхождении заставляет переделывать обе стороны одновременно.
Скелет и CI такого риска не несут, поэтому сначала фиксируется контракт.

- [contracts/dataset-package-v1.md](contracts/dataset-package-v1.md) — спецификация `dataarena.package/1` 1.0.0;
- [contracts/schema/](contracts/schema/) — JSON Schema draft 2020-12 на все пять файлов пакета;
- [contracts/reference/](contracts/reference/) — эталонные реализации отпечатка, валидатора и сборки пакета;
- [contracts/golden/](contracts/golden/) — эталонный пакет и шесть негативных фикстур, все семь проверены;
- [contracts/RECONCILIATION.md](contracts/RECONCILIATION.md) — история согласования двух независимых предложений.

Каталог `docs/contracts/` побайтово идентичен в обоих репозиториях (в ModelArena лежит
по пути `contracts/dataset-package/v1/`). Обязательства потребителя — в ModelArena.

**Формат заморожен 2026-09-06**, тег `contract/dataset-package-v1.0.0` в обоих
репозиториях. Все шесть условий §J выполнены и проверены запуском:

| # | Условие | Состояние |
|---|---|---|
| J-1 … J-4 | спецификация, схемы, 14 фикстур, producer-проверки | ✅ |
| J-5 | независимая consumer-реализация на том же наборе фикстур | ✅ 14 из 14 |
| J-6 | отпечаток воспроизведён на разных версиях Polars | ✅ 1.20.0, 1.43.0, 1.44.1 |

Путь к freeze стоил трёх ревизий формата, и все три вызваны находками потребителя.
ModelArena реализовала алгоритм **по тексту спецификации, не читая эталон**, и нашла
шесть дефектов — два блокирующих. Главный: текст и эталон брали порядок колонок
из разных мест, на golden package это не проявлялось, а на пакете с расходящейся схемой
две добросовестные реализации посчитали бы разные отпечатки.

Отсюда практический вывод для дальнейшей работы: **отчёт другой стороны не заменяет
прогона её кода на своём наборе**. Один такой запуск закрыл вопрос, на который ушло
четыре обмена письмами.

**Stage 1 разблокирован и идёт параллельно на обеих сторонах.**

## Этап 2 — Workspace, форматы, таблица

Самый крупный этап: здесь появляется то, чего в AutoDataAnalysis не было архитектурно.

**Backend**

- `WorkspaceStore` на SQLite: workspace, datasets, версии;
- файловое хранилище `sources/` и `derived/`, пути только из проверенных ID;
- загрузка файла: потоковая запись с лимитом (перенос из `api/uploads.py`), определение
  формата, извлечение схемы, вычисление sha256;
- реестр форматов с объявленными capabilities: CSV, TSV, Parquet, JSON, JSONL/NDJSON,
  XLSX, Feather, Arrow IPC — **чтение**;
- конвертация в Parquet в `derived/` для форматов без `scan_*` (XLSX, JSON) — чтобы lazy-путь
  работал для всех;
- lazy-чтение по умолчанию, материализация — только явная;
- `GET /datasets/{id}/rows` с серверной пагинацией, сортировкой и фильтрами;
- `GET /datasets/{id}/columns/{name}` — статистики колонки для панели.

**Frontend**

- раздел **Workspace**: список датасетов, загрузка, схема, размеры, переключение;
- раздел **Dataset**: таблица с virtual scrolling, сортировкой, resize и reorder колонок,
  управлением видимостью, индикаторами типа и null;
- панель колонки по клику на заголовок: dtype, null %, unique, min/max, mean/median,
  частые значения, распределение, примеры.

**Проверка:** открыть 4 файла разных форматов одновременно, пролистать 1M строк,
отсортировать по колонке, посмотреть панель колонки. Замерить время отклика.

## Этап 3 — SQL Workspace

- `DuckDBSession`: регистрация датасетов workspace → `enable_external_access=false`
  → `allow_community_extensions=false` → `lock_configuration=true` (порядок обязателен,
  проверен в AUDIT A-2);
- второй рубеж: только читающие statements, лимит длины, таймаут, отмена запроса;
- `POST /workspaces/{ws}/sql` — результат + время выполнения + число строк;
- SQL history в SQLite: текст, timestamp, workspace, длительность, повтор, удаление;
- Saved Queries: сохранить, переименовать, изменить, удалить, выполнить;
- frontend: редактор с подсветкой, выполнение, отмена, таблица результата, понятные ошибки,
  панели истории и сохранённых запросов.

**Проверка:** запрос с `JOIN` двух датасетов; перезапуск приложения — история и сохранённые
запросы на месте; набор попыток обхода песочницы — все отбиты; долгий запрос отменяется.

## Этап 4 — Dataset Health

- перенос профилирования из AutoDataAnalysis (`domain/profiling/`);
- **новое:** correlation (Pearson/Spearman), missingness patterns, duplicate groups,
  near-zero variance, duplicate features;
- **выбросы с drill-down:** не счётчик, а строки — `row_id / value / method / threshold`;
  методы IQR и robust z-score (MAD), метод выбирается пользователем;
- единая модель находки: что, где, почему, каким методом, что можно сделать, `drilldown`-запрос;
- suspicious columns — с объяснением причины, **без утверждений о leakage** (нет target — нет утверждения);
- frontend: раздел **Health**, у каждой находки «Подробнее» открывает конкретные строки в таблице.

**Проверка:** на датасете с известными проблемами каждая находка раскрывается до строк;
цифры сходятся с посчитанными вручную.

## Этап 5 — Transformations, pipeline, undo/redo

- `Step` с `validate / apply / describe / preview_impact`, реестр операций;
- операции: drop, rename, reorder, cast, duplicate, derive; delete rows, filter, sort;
  replace, fill missing, find/replace; deduplicate, trim, normalize nulls, normalize casing,
  parse numeric/date — логика переносится из `etl/engine.py`;
- executor: replay списка шагов поверх `LazyFrame`;
- **исходный файл не изменяется никогда**;
- undo/redo как перемещение по списку, удаление шага, reorder с проверкой зависимостей
  по читаемым/записываемым колонкам;
- preview перед применением любой разрушающей операции;
- frontend: редактор pipeline, сравнение «до/после» (перенос `ComparisonPanel`).

**Проверка:** 6 шагов, удалить третий, вернуть, поменять два местами, увидеть отказ
на небезопасной перестановке с объяснением; исходный файл побайтово не изменился.

## Этап 6 — Dataset Builder и joins

- анализ ключей: dtype compatibility, value overlap, uniqueness каждой стороны, null rate,
  тип связи 1:1 / 1:N / N:M;
- **оценка числа строк результата до выполнения** и явное предупреждение о row explosion,
  особенно для N:M;
- join: inner / left / right / full, составные ключи, выбор колонок с каждой стороны,
  стратегия конфликта имён (суффикс задаётся пользователем, а не `_file_N`);
- join preview отдельно от полного выполнения;
- builder: план сборки — источники, соединения, выбор колонок, шаги; результат становится
  датасетом workspace со своим pipeline;
- frontend: визуальный **Builder** со схемами, связями и preview.

**Проверка:** собрать датасет из CSV + JSON + Parquet, увидеть предупреждение о росте строк
до выполнения, сверить фактический результат с оценкой.

## Этап 7 — Smart Join Suggestions

- перенос и расширение `_recommend_merge` / `_select_join_key`;
- предложение содержит: колонки, совместимость типов, overlap, uniqueness обеих сторон,
  null rate, тип связи, confidence и **причину рекомендации** обычным языком;
- никаких догадок без объяснения;
- frontend: карточки предложений с кнопкой «Preview Join» (переиспользуется `RecommendationList`).

**Проверка:** на трёх датасетах с общими ключами — предложения корректны; на датасетах
без связи предложений нет, а не выдуманы.

## Этап 8 — Export

- writers: CSV, TSV, Parquet, JSON, JSONL, XLSX, Feather, Arrow;
- Export Dialog: строки, колонки, формат, оценка размера, сжатие, настройки формата;
- **предупреждения из реестра capabilities, а не из зашитых строк**: JSON/NDJSON теряют
  Date/Datetime (измерено, AUDIT A-3), XLSX ограничен 1 048 576 строк, CSV не хранит типы;
- экспортируются: датасет после правок, результат SQL, результат Builder, промежуточный
  результат pipeline;
- round-trip-тест на каждый формат — обязательное условие попадания в реестр.

**Проверка:** экспорт в 8 форматов, обратное чтение, сверка схемы и данных; предупреждения
появляются именно там, где потеря реальна.

## Что сознательно откладывается за пределы v1

| Отложено | Причина |
|---|---|
| SQLite как источник данных, ORC, Avro-чтение, сжатые CSV/JSON | сначала стабильно закрыть 8 заявленных форматов; добавление — по реальной потребности |

| Ветвление и слияние версий датасета | требование ТЗ — «лёгкий понятный lineage», а не Git для данных |
| Плагины и пользовательские операции | сначала реестр операций должен устояться на встроенных |
| Распределённая обработка | однопользовательский инструмент; вертикального масштаба хватает |
